Custom Skills
Turn your repeated 'watch the build' request into a single /watch-build command with a fixed polling strategy and report format.
Why for you: You made the same request in all 3 sessions. A skill would give you consistent, low-noise monitoring and a clear pass/fail result every time.
mkdir -p .claude/skills/watch-build && cat > .claude/skills/watch-build/SKILL.md <<'EOF'
---
name: watch-build
description: Monitor the current CI build until it completes and report the result
---
1. Identify the latest run for the current branch (e.g. `gh run list --branch $(git branch --show-current) --limit 1`).
2. Wait for it with ONE blocking command: `gh run watch <id> --exit-status --interval 30`.
3. On failure, run `gh run view <id> --log-failed | tail -50` and summarize the root cause.
4. Finish with: BUILD <PASSED|FAILED> — <id> — <duration> — <suggested next step>.
EOF

AI-assisted development is shifting from Claude polling a build on request to Claude owning the whole build-test-fix loop and returning clear, verified outcomes.

Self-Healing Build Watcher With Auto-Fixes
Instead of polling a build with roughly 30 Bash calls and stopping without a verdict, Claude can watch the build to completion, read any failure logs, find the root cause, and push a fix. It can repeat this loop until the build is green or it hits a clear blocker. Every session would end with a definitive outcome and a summary of what changed.
Getting started: Give Claude the build command or CI status command (for example, `gh run watch` or `gh run view --log-failed`). Ask it to loop on failures and use backoff sleeps instead of rapid polling.
PASTE INTO CLAUDE CODE:
Watch the current build until it finishes. Use backoff polling: wait 30s, then 60s, then 120s between checks, and never make more than 15 status checks. When it finishes, report clearly: PASSED or FAILED, with duration. If it FAILED: 1) pull the failing logs (e.g. `gh run view --log-failed`), 2) identify the root cause and quote the key error lines, 3) make the minimal code fix, 4) re-run the relevant build or test step locally to verify, 5) repeat up to 3 times. End with a summary table listing each attempt, the error, the fix applied, and the result. Do not stop without an explicit final verdict.

Parallel Agents Triage Multi-Job Failures
When a CI pipeline has several jobs (lint, unit tests, integration tests, builds for different platforms), Claude can start parallel sub-agents, one per failing job. Each agent investigates and drafts a fix on its own, then a coordinating agent merges the results and checks for conflicts. Triage that used to happen one job at a time finishes in a single pass.
Getting started: Use Claude Code's Task/sub-agent tool to run one investigator per failing CI job. Have it use git worktrees so the fixes don't collide.
PASTE INTO CLAUDE CODE:
List all jobs in the latest CI run and their status. For each failed job, launch a separate sub-agent with these instructions: fetch that job's logs, find the root cause, and propose a minimal fix in its own git worktree, verified by re-running only that job's command locally. After all sub-agents finish, combine their fixes into one branch and resolve any conflicts. Then run the full local test suite. Report a per-job breakdown with the root cause, the fix, and whether the fix was verified. Finally, give an overall go/no-go recommendation for pushing.
