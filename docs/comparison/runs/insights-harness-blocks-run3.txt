Custom Skills
Turns a repeated workflow into a single /command.
Why for you: 'Watch the build' was your only goal across all 3 sessions. A /watch-build skill would encode the efficient wait strategy and the reporting format once, so you don't have to re-explain them each time.
mkdir -p .claude/skills/watch-build && cat > .claude/skills/watch-build/SKILL.md <<'EOF'
---
name: watch-build
description: Wait for the current CI build to finish and report the result
---
1. Find the latest run for the current branch: `gh run list --branch $(git branch --show-current) --limit 1`
2. Block until it finishes with `gh run watch <id> --exit-status` (do NOT poll with repeated short commands).
3. On failure, run `gh run view <id> --log-failed` and summarize the failing step and the key error lines.
4. End with `BUILD: PASSED` or `BUILD: FAILED - <reason>`, plus suggested next steps.
EOF

On the Horizon

Build monitoring is moving from Claude polling a status in a loop to agents that wait on events, figure out why a build failed, and push fixes without being asked.

Self-Healing Builds That Fix Their Failures
Right now Claude spends about 30 Bash calls per session just checking whether the build has finished. Instead, an agent could wait for the build to finish, read the failure logs, find the root cause, apply a fix, and rebuild, repeating until the build passes. You would only hear about it when it is green or when a decision needs a person.
Getting started: Use headless mode (`claude -p`) with a build command that blocks until done, or one that streams its logs, so Claude isn't polling repeatedly. Give it permission to edit files and re-run the build, and set a limit on how many retries it can attempt.
PASTE INTO CLAUDE CODE:
Run the build and wait for it to finish using a single blocking command (e.g. stream logs or use a CLI 'watch' flag) instead of polling repeatedly. If it fails: 1) extract the first real error from the logs, 2) identify the root cause in the source, 3) apply the smallest fix, 4) rebuild. Repeat up to 5 times. When done, give me a short report covering final status, each failure you hit, what you changed, and anything you weren't confident about. Do not commit; leave changes staged for my review.

Parallel Agents Triage Multi-Stage Pipelines
One Claude watching one build in a loop could become several sub-agents, each covering one stage: compile, tests, lint, and packaging. When a stage fails, its agent immediately starts investigating, so diagnoses come in parallel rather than one after another. A coordinating agent then combines their findings into a single triage summary.
Getting started: Use the Task tool to start one sub-agent per pipeline stage or CI job, then have the main session merge their results. This works well with CI CLIs like `gh run watch` or `gh run view --log-failed`.
PASTE INTO CLAUDE CODE:
List the jobs in the latest CI run. For each job, start a separate sub-agent that waits for that job to finish. If the job fails, the sub-agent should pull only the failed logs, classify the failure (flaky test, real regression, infra/env issue, dependency issue), and propose a fix with file and line references. Then combine all sub-agent results into one table with these columns: job, status, failure category, root cause, proposed fix, confidence. Recommend which fixes to apply first.
